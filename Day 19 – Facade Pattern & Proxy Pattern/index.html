📖 Introduction to Structural Design Patterns

Structural Design Patterns explain how classes and objects are organized to build larger and more flexible software systems.

They reduce complexity, improve maintainability, and encourage code reuse.

Why use Structural Design Patterns?

  • Improve code reusability
  • Simplify complex systems
  • Increase flexibility
  • Improve maintainability
  • Create scalable applications

🏢 Facade Pattern

Definition

The Facade Pattern provides a simple interface to a complex subsystem. Instead of interacting with multiple subsystem classes, the client communicates with a single Facade class.

Why Facade Pattern?

Imagine starting a computer. You simply press the Power Button. Internally, many operations happen automatically such as starting the CPU, loading memory, and reading the operating system. The Power Button acts as the Facade.

Real-Life Examples
  • Computer Startup
  • ATM Machine
  • TV Remote
  • Hotel Booking System
  • Online Shopping Checkout

Components of Facade Pattern

  • Client – Uses the Facade instead of interacting with subsystem classes directly.
  • Facade – Provides a simple interface to the complex subsystem.
  • Subsystem Classes – Perform the actual operations behind the scenes.

Facade Pattern Workflow


Client
   │
   ▼
Facade
   │
   ▼
Subsystem Classes

The client communicates only with the Facade. The Facade internally coordinates all subsystem classes and returns the required result.

Advantages

  • Simplifies complex systems.
  • Reduces coupling between client and subsystem classes.
  • Improves code readability.
  • Makes maintenance easier.
  • Provides a single entry point to the subsystem.

Disadvantages

  • The Facade class can become too large if not designed properly.
  • Advanced subsystem features may be hidden from the client.
  • An extra abstraction layer may be introduced.

Real-Time Applications

  • Computer Startup Process
  • ATM Machine Operations
  • TV Remote Control
  • Hotel Booking Systems
  • Spring Framework
  • JDBC API
  • E-commerce Checkout Systems

The Facade Pattern hides the complexity of multiple subsystem classes by exposing a single, easy-to-use interface.

🔒 Proxy Pattern

Definition

The Proxy Pattern is a Structural Design Pattern that provides a placeholder or representative object to control access to another object. Instead of communicating directly with the real object, the client interacts with the Proxy.

The Proxy can perform additional tasks such as security checks, logging, caching, or lazy initialization before forwarding the request to the real object.

Why Proxy Pattern?

Imagine visiting a company's office. Before meeting the manager, you first interact with the Security Guard. The guard verifies your identity and decides whether you are allowed to enter. Here, the Security Guard acts as the Proxy, while the Manager represents the Real Object.

Components of Proxy Pattern

  • Subject – Defines the common interface used by both Proxy and Real Subject.
  • Real Subject – The actual object that performs the requested work.
  • Proxy – Controls access to the Real Subject.
  • Client – Uses the Proxy instead of directly accessing the Real Subject.

Proxy Pattern Workflow


Client
   │
   ▼
Proxy
   │
   ├── Access Allowed?
   │
   ├── Yes ─────► Real Object
   │                   │
   │                   ▼
   │             Perform Task
   │
   └── No
         │
         ▼
    Access Denied

The client sends a request to the Proxy. The Proxy checks whether access is allowed. If permitted, it forwards the request to the Real Object; otherwise, it denies access.

Advantages

  • Provides controlled access to objects.
  • Improves application security.
  • Supports lazy object creation.
  • Adds logging and monitoring.
  • Can cache frequently used data.

Disadvantages

  • Adds an extra layer between client and object.
  • May slightly reduce performance due to additional checks.
  • Can increase design complexity if overused.

Real-Time Applications

  • Security Guard at Office
  • ATM Card Authentication
  • Proxy Servers
  • Spring AOP
  • Hibernate Lazy Loading
  • Java RMI
  • Cloud Storage Access Control

The client communicates only with the Proxy, which decides whether the request should reach the Real Subject.

Key Point:

The Proxy Pattern controls access to an object by acting as an intermediary, providing security, logging, caching, or lazy initialization without modifying the original object.

⚖️ Facade Pattern vs Proxy Pattern

Facade Pattern Proxy Pattern
Provides a simplified interface to a complex subsystem. Controls access to another object.
Focuses on reducing complexity. Focuses on security and access control.
Hides subsystem details. Acts as an intermediary between client and real object.
Improves usability. Improves security and performance.
Client communicates with the Facade. Client communicates with the Proxy.

✅ Best Practices

  • Use the Facade Pattern to simplify interactions with complex subsystems.
  • Use the Proxy Pattern when access control or security is required.
  • Keep Facade classes focused on one subsystem.
  • Avoid putting too much business logic inside the Facade.
  • Use Proxy for logging, caching, lazy loading, and authentication.
  • Follow the Single Responsibility Principle (SRP).

📌 Conclusion

The Facade Pattern simplifies communication with complex systems by providing a single, unified interface to multiple subsystem classes.

The Proxy Pattern controls access to an object by acting as an intermediary, enabling features such as security, lazy loading, logging, and caching.

Both patterns are widely used in enterprise Java applications, Spring Framework, Hibernate, and other real-world software systems to improve maintainability, flexibility, and scalability.
